# AGENTS.md

Working agreement for coding agents in this repo. This file is the always-loaded layer; deeper detail lives behind the pointers here. When something here and a doc disagree, the doc wins for *why*, this file wins for *how to behave*.

## What this project is

gowit: a lightweight, cross-platform Git GUI. Go backend, Wails v2 shell, React + TypeScript frontend. Read [`README.md`](README.md) for goals, [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for decisions and their reasoning, [`docs/STRUCTURE.md`](docs/STRUCTURE.md) for the target layout.

## Commands

```bash
go build ./ ./internal/...                 # compile backend
go vet ./ ./internal/... && gofmt -l .     # must both be clean before any commit
go test -cover ./ ./internal/...           # backend tests with coverage
wails dev                                  # hot-reload dev app
wails build                                # production binary into build/bin/
cd frontend && npm run lint && npm run test && npm run build  # frontend
```

Scope Go commands to `./ ./internal/...`: `./...` also matches stray Go files under `frontend/node_modules` (e.g. `flatted/golang`) and drags them into builds.

Dependencies: Go ≥ 1.25 (Wails v2.16 floor), Node ≥ 20, `git` on PATH, Wails CLI (`go install github.com/wailsapp/wails/v2/cmd/wails@latest`).

## Architecture guardrails

These come from ARCHITECTURE.md. Violating one is a review block, not a style opinion.

1. **All git operations shell out to the system `git` CLI** through one `runGit()` in `internal/git/`. Use `--porcelain`/`--porcelain=v2` for anything parsed. No cgo, no libgit2, no go-git.
2. **`app.go` methods are thin adapters.** Parse arguments, call into `internal/*`, return results. Logic lives in `internal/git/`, `internal/watcher/`, `internal/config/`, where it is testable without the Wails runtime.
3. **Long-running operations emit progress** via `runtime.EventsEmit`; they do not block a bound call.
4. **Errors crossing the boundary are typed structs** (code + message), never bare strings.
5. **Never hand-edit `frontend/wailsjs/`**; it is generated by `wails dev`/`wails build`.
6. `frontend/dist` exists as an embed placeholder; the real frontend arrives in issue #4. Until then keep `frontend/src/main.js` minimal.

## Workflow: the skills pipeline

The `skills/` folder holds the team skill library (local only, gitignored). Skills are the process; this file is the context. Main flow for new work:

`/grill-with-docs` (or `/grilling`) → optionally `/prototype` → `/to-spec` → `/to-tickets` → one `/implement` per ticket (driving `/tdd`, closing with `/code-review`) → commit.

On-ramps: `/triage` for issues and external PRs you did not create, `/diagnosing-bugs` for hard bugs, `/wayfinder` for large foggy efforts, `/ask-matt` when unsure which fits. Read the matching `SKILL.md` under `skills/` before acting; follow it literally.

Context hygiene: planning stays in one unbroken context window through `/to-tickets`; each `/implement` starts fresh. Specs, tickets, and briefs avoid file paths and code snippets, since they go stale; describe behavior, reference issues by number.

## Design standards

- **Design lint gates UI changes.** After touching `frontend/`, run `npm run lint` (@shadcn/lint) and fix all errors. Component styling contracts live in `frontend/eslint.config.mjs`; extend them instead of restyling primitives with raw classes.
- **YAGNI first.** No speculative generality, no hooks for imagined futures. Prefactor: make the change easy, then make the easy change.
- **Deep modules** (see `skills/engineering/codebase-design/`): small interface, real implementation behind a clean seam. Apply the deletion test to anything suspected shallow. Use that skill's vocabulary exactly: module, interface, implementation, depth, seam, adapter, leverage, locality. Avoid "component", "service", "boundary".
- **DRY without premature abstraction.** Duplicated code is a review smell; a wrong abstraction is worse. Two similar blocks mean look for the real concept, not a helper.
- **One adapter means a hypothetical seam. Two means a real one.** Do not build ports nobody implements.
- When a domain term is fuzzy or contested, resolve it and record it in `CONTEXT.md` (glossary only, no implementation details). Write an ADR in `docs/adr/NNNN-slug.md` only when the decision is hard to reverse, surprising without context, and the result of a real trade-off. Otherwise skip it.

## Testing

- **TDD, vertical slices.** Red before green: one failing test, then the minimum code to pass, then repeat. Never write all tests first, then all implementation.
- **Tests verify behavior through public interfaces.** Expected values come from an independent source of truth (a worked example, a known-good literal, the spec), never from the implementation under test. A test that changes when the implementation changes is testing past the interface.
- **Agree the seams before writing tests.** State which interface each slice exercises; if no correct seam exists, that is an architectural finding, raise it instead of testing around it.
- **Mock only at system boundaries** (network, time, randomness). Never mock your own packages. For git code, run real `git` against `t.TempDir()` repos; test actual behavior, per ARCHITECTURE.md §9.
- **Accept dependencies, don't create them.** Pass them in so tests drive the same interface callers do.
- **Coverage: 100% of changed code is the bar.** `go test -cover ./...` for backend, coverage thresholds in the frontend vitest config (set up in #4). Uncovered lines need a reason stated in the PR; dead code placeholders get deleted, not exempted.
- Bugfixes need a reproduction first: a fast, deterministic, agent-runnable command, then reproduce, minimise, and only then hypothesize. Put the confirmed hypothesis in the commit message.

## Git and PRs

- Branches: `feature/#<issue>-<slug>` or `fix/#<issue>-<slug>`. Conventional commits: `feat|fix|chore|docs|refactor(scope): summary`, body explains *what/why*, one logical change per commit.
- Each ticket gets its own PR, linked `Closes #<N>`. Run `/code-review` (standards axis + spec axis, in parallel) before opening it.
- Commit only when asked. Never push, force-push, or open PRs without the user requesting it. Do not commit secrets; redact values in any pasted output as `<REDACTED>`.
- Merge conflicts: resolve hunk by hunk preserving both sides' intent, run vet/tests after; never `--abort` without the user's agreement.

## Communication style

`skills/engineering/unslop/SKILL.md` applies to every artifact an agent produces (code comments, docs, PR text, chat replies): active voice, specifics over atmosphere, no AI vocabulary, no sycophancy or filler, no em dashes in prose, sentence-case headings. When the user signals confusion, re-explain in plain Simplified Technical English using the `CONTEXT.md` vocabulary before continuing.

## Decisions belong to the user

Facts are the agent's job: look them up, dispatch sub-agents to read code or docs, never ask the user what a file says. Decisions are the user's job: present numbered questions with a recommended answer, then wait. Do not start implementing out of a planning conversation until the user confirms shared understanding.
